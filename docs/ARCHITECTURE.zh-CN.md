# 架构说明

[中文](ARCHITECTURE.zh-CN.md) | [English](ARCHITECTURE.md)

这份文档不是写给只想快速部署的人看的。
如果你已经能跑起来，想进一步理解“为什么推荐这样部署”，再看这份文档会更合适。

## 一句话理解

这个项目的核心思路是：

不要把 Codex 直接暴露到公网，
而是在你自己的电脑上本地运行，再通过一个尽量收敛的私有网页入口，让手机只做“查看和聊天控制”。

## 为什么不直接把应用暴露出去

因为你控制的是电脑上的本地 Codex，会话权限通常很高。
如果暴露方式太粗糙，风险会很大，比如：

- 别人撞库后直接登录
- 公网扫描直接碰到你的服务
- 高风险接口暴露过多
- 新设备拿到账号密码后立刻登录成功

所以这个项目的目标不是“最省事”，而是“自己用时尽量安全、尽量可控”。

## 推荐结构

推荐的运行方式如下：

```text
手机浏览器
   ↓
Tailscale 私网 HTTPS
   ↓
本机 nginx
   ↓
本机 claudecodeui（已应用本项目补丁）
   ↓
本地 Codex 会话
```

## 每一层分别负责什么

### 1. 手机浏览器

它只负责：

- 看项目
- 看会话
- 发消息

它不是完整管理端，也不是远程桌面。

### 2. Tailscale 私网

它负责把访问范围先限制在“你自己的设备网络”里。

这样做的好处：

- 减少公网暴露
- 设备接入和手机访问更简单
- 适合个人长期使用

### 3. nginx

它是网页入口前面的代理层，主要负责：

- 统一入口
- 转发到本地应用
- 附加安全头
- 登录限流
- 让 Node 应用继续只待在 localhost

### 4. claudecodeui + 本项目补丁

这一层负责：

- 提供网页界面
- 提供项目 / 会话 / 消息接口
- 支持手机端交互
- 增加 hardened mode 下的收敛行为
- 增加设备白名单与首次审批能力

### 5. 本地 Codex 会话

真正执行工作的是这里。
手机不是直接运行 Codex，而是在控制电脑上本地已经存在的 Codex 会话和项目。

## 手机端发送中的消息

手机端向桌面 Codex 发送消息时，前端会先显示一条“发送中”的本地 pending 消息，等桌面 Codex 同步到同一条用户消息后再标记为已发送。

当前实现保持轻量边界：

- 同一个会话只持久跟踪最后一条 pending 消息
- “发送中”状态下仍允许继续输入和发送下一条消息
- 最后一条“发送中”消息上的“删除”按钮只删除前端 pending 显示和本地 pending 记录
- 删除按钮不会取消已经进入桌面自动化队列的真实发送任务

### 如何判断“发送成功”

前端不会只根据 HTTP / WebSocket 请求返回来判断发送成功，也不会自己用当前渲染出来的消息列表做最终判断。
真正的成功条件由后端统一判断：后端读取完整 Codex JSONL 历史，确认里面已经出现同一条用户可见消息。

前端会把最后一条 pending 的内容和时间戳发给后端的 pending-delivery 检查接口。后端会在完整历史里做内容归一化和时间窗口匹配，返回 `sending`、`sent` 或 `failed`。如果超过 60 秒仍未在完整 Codex 历史里找到这条消息，后端会判定为 `failed`；前端只消费这个结论来更新状态。

如果用户点击最后一条 pending 消息上的“重发”，前端会复用这条本地 pending 气泡，把状态重置为 `sending`，并用当前时间重写 pending 时间戳。这样后端的 60 秒失败窗口会从重发时间重新开始，而不是沿用上一次失败发送的旧时间。

输入框左侧状态按钮会区分发送链路和回答链路：`sending` 显示“发送中”，`failed` 显示“发送失败”；当 Codex 会话仍在处理且没有未确认发送，或最新消息已确认 `sent` 时显示“回复中”；空闲时显示完成状态。侧边栏会复用同一套判断显示会话状态：所有已加载会话都会显示徽标，单会话项目直接把状态挂在项目行上，多会话项目行显示已加载会话的汇总状态。为了让后台会话也及时更新，App 顶层会定期请求已加载会话的 `session-status`；侧边栏状态徽标在 `sending` 时也会直接调用后端 pending-delivery 检查接口。

消息分页仍会尽量包含最新用户消息，但这个设计只服务于页面显示，不再作为“是否发送成功”的判断来源。

这个判断只用于“最后一条 pending”。如果同一会话连续快速发送多条，前端仍然只持久跟踪最后一条，这是有意为之：保持实现轻量，并避免让前端误以为可以取消已经进入桌面自动化队列的旧发送任务。

## 手机端到桌面 Codex 的发送链路

手机端发消息不是直接调用 Codex CLI，也不是新建会话。
它走的是“控制电脑上已经打开的 Codex 桌面窗口”这条路径：

```text
手机网页
   ↓ WebSocket / HTTP
本机 claudecodeui 后端
   ↓ desktop bridge 队列
Codex 桌面自动化 worker
   ↓ UIA / Win32 控制
本机 Codex App 现有项目和会话
```

这条链路的设计边界是：

- 手机只表达“给某个已有 Codex 会话发送这段文本”
- 后端负责解析项目、会话和 Codex 历史元数据
- 桌面自动化只负责打开正确会话、写入输入框、触发发送
- Codex 真正的回复仍然由桌面 App 内的原会话产生
- 手机再通过同步 Codex 历史来看到最终消息

### 为什么使用桌面窗口控制

当前目标是更新 Codex App 里的真实会话，而不是维护一份平行会话。
所以手机端不能只把消息写进网页数据库，也不应该新建一个独立 session。

使用桌面窗口控制的好处是：

- Codex App 里能看到同一条用户消息
- 手机和电脑最终基于同一份 Codex 历史
- 不需要逆向或依赖未公开的桌面内部接口

代价是：

- 电脑必须处于可交互桌面
- Codex App 必须运行并能被窗口自动化找到
- 屏保、锁屏、窗口状态异常都会影响发送

发送消息时，桌面自动化会临时禁用 Windows 屏保，并继续执行唤醒显示器、关闭当前屏保窗口、发送轻量输入等兜底动作。`send-message` 结束后会恢复原来的屏保启用状态，避免永久修改用户的系统设置。锁屏不属于屏保，仍然需要用户回到可交互桌面。

### worker 与 one-shot 的关系

默认优先使用常驻桌面自动化 worker。
这样可以避免每次发送都重新初始化 UIA，提高手机点击发送后的响应速度。

但 worker 必须满足两个条件：

- 启动后能在限定时间内输出 ready
- 每次请求能在限定时间内返回结果

如果 worker 启动阶段失败，后端会回退到 one-shot 自动化。因为这时还没有执行真实发送动作，回退是安全的。
如果 worker 已经开始执行 `send-message` 后失败，后端不会再自动重试发送，避免同一条消息被重复发送。

### worker 进程回收

Windows 下 PowerShell 会再启动 Python，Python 里又可能加载 UIA 相关组件。
如果只杀 PowerShell 壳，Python 子进程可能残留，最终造成“前端发了、后端收到、但 Codex 窗口没动作”。

因此现在的设计是：

- worker ready 超时要终止整棵进程树
- worker 请求超时也要终止整棵进程树
- Windows 下使用 `taskkill /T /F`
- 清掉坏 worker 后，下次发送可以重新建立干净 worker

### Codex 窗口连接方式

桌面自动化不再用 UIA 全局窗口搜索来找 Codex。
当前策略是：

1. 先用 Win32 `FindWindow("Chrome_WidgetWin_1", "Codex")` 找到 Codex 主窗口句柄
2. 再用 pywinauto UIA 按 handle 连接这个窗口
3. 后续控件查找、会话选择和输入发送继续走 UIA / Win32 混合控制

这样做是为了避开某些机器上 `Desktop(backend="uia").window(...)` 全局搜索卡住的问题。

## 项目和会话同步设计

前端显示的项目和会话不应该只来自网页侧缓存。
对于 Codex-only 模式，后端会从 Codex 历史和桌面元数据重新建立项目 / 会话索引，并过滤掉已经不存在的本地项目。

设计原则是：

- 本地路径不存在的普通项目不显示
- 已归档项目不显示
- 项目名显示文件夹名，不显示完整路径
- 只有一个会话的项目，侧边栏点击项目可以直接打开会话
- 只有一个会话的项目不需要展开，thinking 状态和会话名直接显示在项目行

### 无项目会话

Codex 里可能存在没有匹配本地项目的历史会话。
这类会话不能硬塞进某个真实路径，也不能因为没有项目就彻底消失。

当前设计是把它们归到一个虚拟项目：

- 内部项目名：`__codex_projectless__`
- 内部路径：`codex://projectless`
- 前端显示名：`无项目会话`

这个虚拟项目不会做本地路径存在性检查。
发送消息时，如果用户打开的是无项目会话，前端会优先使用会话自己的 `cwd` 作为 desktop bridge 的项目路径；如果没有 `cwd`，才回退到虚拟项目信息。

## 为什么一定要保留“首次设备审批”

这是这个项目最值得保留的安全边界之一。

如果没有这个机制，那么：

- 只要有人拿到账号密码，就可能直接从陌生设备登录

有了它以后：

- 新设备第一次登录时必须在电脑端批准
- 电脑主人可以看设备名、平台、UA、IP
- 只有批准后的设备才进入白名单

这对“只有自己用”的远程控制面板非常重要。

## 为什么既有 Cookie，又有 Bearer / WebSocket fallback

因为不同手机环境不一样。

### 浏览器环境

浏览器通常最适合走：

- 同源 Cookie 会话

### WebView / 封装 App 环境

一些壳在这些方面兼容不稳定：

- Cookie
- WebSocket
- Header
- 本地存储

所以这里保留了兼容层：

- HTTP 请求可走设备绑定 Bearer fallback
- WebSocket 握手可走 token fallback

但重点是：

- 这些 fallback 是为了兼容，不是为了放宽安全边界
- 新设备仍然要经过白名单审批

## 为什么默认保持 hardened mode

因为目标是手机远程控制，不是远程开放所有能力。

默认收敛后，更适合公开发布和个人私用：

- 攻击面更小
- 不容易误开放高风险功能
- 也更容易给别人讲清楚“这个项目到底能做什么”

## 适合的使用方式

最推荐的使用方式是：

- 只有你一个人在用
- 你的电脑是主执行端
- 你的手机是远程查看和发消息端
- 通过私网访问
- 用桌面工具批准新设备

## 不推荐的使用方式

以下场景不建议直接套这个默认架构：

- 多用户共享
- 公网直接裸奔
- 把它当通用远程执行平台
- 在未重新审计前开放更多高风险接口

## 你真正需要记住的重点

如果你不想看太多技术细节，只需要记住这 4 条：

1. 应用留在本机，不直接公网暴露
2. 手机通过私网入口访问
3. 新设备第一次登录必须电脑批准
4. 手机主要负责“查看和聊天控制”，不要默认开放更多高风险能力
