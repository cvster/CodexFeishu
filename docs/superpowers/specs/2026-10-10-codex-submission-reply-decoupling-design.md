# Codex 消息提交与回复同步解耦设计

日期：2026-10-10

状态：待用户书面设计确认；尚未实现、部署或重启。

## 目标与范围

修复飞书消息已收到、但被旧任务的回复观察器长期阻塞的问题。参考当前桌面 App 的公开 app-server 交互方式，让消息提交和回复同步具有独立生命周期。

成功标准：

- Codex 确认接收消息后，同群后续消息能够继续进入官方队列，不必等待上一轮回答结束。
- 会话、轮次与用户消息优先通过 ID 关联，不用提示词文本判断任务是否结束。
- 飞书回复仍由一个同步器写入；不会因两个观察器生成重复卡片。
- 无公开共享 app-server 的本机仍可通过官方 CLI 提交；不接入桌面内部 IPC。
- 同步器断线、读不到轮次或桥接重启，都不自动停止 Codex 任务，也不盲目重发消息。
- 部署前保全既有积压消息；两端代码保持一致，按能力动态选择连接方式。

本次不改 Claude 执行流程，不重构网页适配器，不增加私人 IPC，不重启桌面 App 或共享 app-server。模型、问询、归档、群名同步等既有功能保持兼容。

## 已确认的问题

当前链路在 `channel.ts` 中阻塞群提交队列，直到 `queue.ts` 的整个回复观察过程结束。官方 CLI 已确认接收消息，但观察器仍需要找到对应轮次才能退出。

AA-ota-driver 的旧消息在 2026-10-09 22:49 已被官方队列接收，对应轮次也已完成。CLI 保存的用户文本附带换行，而桥接通过严格文本相等寻找轮次，导致始终没有找到。观察器未退出，因此后续消息只进入桥接内存队列，未提交给 Codex。

这不是仅修剪换行可以根治的问题：重复文本、快速完成、断线重连和 CLI 自生成 client ID 都可能使文本关联不可靠。观察器未结束也不等于 Codex 仍在执行。

## 方案选择

采用“独立提交器 + 现有统一回复同步器”。提交器只负责可靠提交和记录接收结果；同步器独立读取真实轮次及运行状态。

不采用以下替代方案：

- 只修剪文本或增加等待超时：可缓解本例，但仍把消息提交绑在回复观察器上。
- 使用桌面内部 IPC：会扩大兼容风险，且本次只使用公开协议和官方 CLI。

参考依据是本机安装的桌面 App bundle 与本地 `openai-codex-reference`：App 使用 `thread/queue/add` 的 `clientUserMessageId`、返回的 queue ID、`thread/queue/list` 和队列变化通知管理提交；使用轮次完成通知和状态快照处理回答结束。队列方法属于公开的实验性协议，需要能力检测，不能假定所有版本都支持。官方文档的事件与状态说明见 [App-server 文档](https://developers.openai.com/codex/app-server)。

## 组件职责与接口

### 1. 提交器

在 Codex core 中增加独立的提交接口，返回接收结果，而不是用 `AgentEvent.done` 表示消息被接收。

输入包含 thread ID、原始用户输入、稳定的桥接 submission ID 和 client user message ID。飞书回复目标保存在桥接状态中，不添加到用户提示词里。

结果至少区分：

- `accepted`：取得官方接收确认，包含可取得的 queue ID/client ID。
- `rejected`：明确拒绝且未接收，可以展示具体错误。
- `unknown`：发送后未取得确认，不能断言未提交，禁止自动重发。

提交状态不冒充任务状态。`accepted` 不表示回答完成，`unknown` 不显示为任务执行失败。

### 2. 群内提交调度

保留现有消息合并与约 600ms debounce。每群只串行处理提交动作，不串行等待回答。

接收确认后立即释放当前群的提交锁；后续消息交给官方队列排序。明确拒绝或未知接收结果也结束本次提交等待，保留诊断记录，并明确提示用户。不会因一个不可关联的回复持续堵塞群。

超时只终止桥接的等待，不取消官方已接收消息或正在进行的轮次。显式“停止”仍走独立取消逻辑。

### 3. 统一回复同步器

复用 `codex-turn-sync.ts`，继续以 thread ID、turn ID 和目标群作为交付键。移除 Codex 提交路径中承担任务生命周期的逐请求回复观察器；不新增第二个卡片输出路径。

提交前记录该会话的基线轮次与回复目标，接收后补充 queue/client ID。该过程支持轮次在确认返回前就开始或完成的竞态。

有 ID 时用 user item 的 client ID 精确关联；无 ID 时，基线和时间窗口只辅助判断消息来源，不能决定任务存活或阻塞提交。重复文本或多候选时不猜测精确对应关系；按照会话绑定同步回答，并避免把不确定的飞书输入再次当成桌面用户消息回显。

已存在的交付记录用于防止重发同一轮次卡片；历史轮次基线用于避免重新补发旧回答。最终状态写入前先排空同轮次尚未处理的内容，防止状态已结束但正文少尾部。

### 4. 权威状态与连接能力

远程或本机存在可用公开共享端点时，使用该端点的队列能力与事件；通过 `turn/completed`、`thread/status/changed` 等通知触发同步，并定期读取快照补偿漏通知。

没有可用公开共享端点时，用现有官方 CLI 提交和只读快照同步。独立 reader 的 `notLoaded` 不解释为真实任务结束，也不解释为任务运行中。状态不可确认时显示同步状态未知，并保留最后一次确认状态。

能力检测要区分端点不可用、方法不支持和实际提交失败。仅在发送前确定原生接口不可用时选 CLI；若原生请求可能已提交，不再自动换 CLI 重发。能力变化在下一次安全提交边界重新检测。

CLI 接收返回的 queue ID 与 CLI 生成的 client ID 不是同一 ID，不进行推导或伪造。能查询官方队列时可补齐映射；不能时记录关联能力受限，但不影响提交锁释放。

## 持久化与异常恢复

以现有 profile state 存储机制增加小型提交记录，不引入数据库或独立 worker。内容包括飞书消息 ID、目标、thread ID、原始输入、提交/client/queue ID、基线轮次、时间和状态；运行数据不提交 Git。

先持久化待提交记录，再发出请求；明确确认后持久化接收结果。写入失败时不开始新提交。已确认对应轮次结束的记录保留 7 天后清理，未确认或未完成的记录不自动删除；卡片交付记录继续遵循现有同步器的保留规则。

重启后：

- 从未尝试发送的待提交记录，在归档和绑定校验后可以恢复提交。
- 已确认接收的记录只恢复同步，不重发输入。
- 曾尝试发送但确认未知的记录，先查官方队列及真实轮次；无法唯一确认时提示用户，不自动重发。

稳定 client ID 是关联标识，不假设服务端以此提供幂等去重。本设计不声称网络故障下实现严格 exactly-once。

归档检查在入队、实际发送和恢复时执行。已归档会话不创建替代会话或新群，沿用既有提示。

## 停止与服务重启

停止按钮通过官方 queue ID 或 turn ID 取消指定排队消息/运行轮次；不知道 ID 时不误取消别的任务。

服务断开只关闭桥接观察和自身连接，保留提交记录，不发送 interrupt/delete，不停止共享 writer 或桌面进程。回复同步与任务执行寿命互相独立。

## 既有积压消息的一次性处理

旧版本积压消息仅在内存中，不能把“重启会恢复”当成现有保证。部署前对 AA-ota-driver 等异常群核对桥接日志、飞书消息历史和真实线程历史，形成不入 Git 的恢复清单。

清单标出：已经接收并完成的旧请求、仅收到而未提交的请求、结果不明的请求。已确认旧请求不重发；确定未提交的消息保留原顺序迁入持久化记录；无法确认的消息先征求用户选择，不盲目重放。按飞书 message ID 去重，不能仅按相同文本去重。

旧服务没有公开内存导出或解除观察器接口时，不通过写入桌面内部状态解除阻塞。先完成恢复清单，再按服务安全规则替换桥接。

## 验证要求

用回归测试覆盖：

- 输入末尾换行变化不会阻塞后续提交。
- 相同文本的两条消息通过不同 ID 区分。
- 轮次在接收确认前完成仍能被同步，且只有一个回复卡片。
- 找不到对应轮次、reader 断线或状态未知不会长期持有提交锁。
- 官方队列暂停时显示排队，不强制启动、不显示完成。
- 接收确认丢失时不自动切换通道或重复提交。
- 桥接重启不终止 Codex 任务，待提交记录不丢失，已接收消息不重放。
- 结束事件先于最后内容处理时，最终卡片仍包含完整正文。
- 显式停止、归档校验、回复目标及桌面外部消息同步仍符合原行为。
- Windows CLI fallback 和 Linux 公开共享端点分别通过测试；Claude 与网页适配器相关测试不回归。

## 部署与验收

完成实现、相关测试、类型检查和构建后，提交并推送 `codexfeishu/main`。备份两端代码、运行状态和恢复清单，部署同一版本。

每次部署前重新检查桥接 active-run、真实 app-server 状态与操作系统进程。若存在当前 AA飞书桥接以外的活动任务，先说明受影响群并取得重启确认。只重启桥接服务，不触碰桌面 App 和共享 app-server。

部署后确认两端版本/构建哈希一致、服务与长连接正常、共享 writer PID 未被部署改变。核对积压恢复结果，并在用户授权的测试会话验证连续提交与最终卡片。若异常，回滚桥接代码，但保留提交记录，不能因回滚重新发送已接收消息。

## 设计自审

此修复只改变 Codex 提交生命周期与其同步协作，复用已有统一卡片同步器；不加入新后台执行系统。ID 缺失、确认不明和连接能力降级均有明确安全行为，不以文本匹配决定任务生命周期，也不以重试假装保证幂等。
